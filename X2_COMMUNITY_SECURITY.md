# X2 research network: implemented security and verification

Prepared 17 November 2026. This extends the existing X1 Body/group model; it does not replace existing handles, memberships, revisions, Supers or comments. The original restricted Site audience is unchanged. Nothing here grants access to someone outside that audience.

## Implemented scope

Community now has nested Groups, Discover, Messages, Saved, Notifications and Privacy views. The universal-search contract is `GET /api/x2/social?view=search&q=...&kind=all|bodies|groups|souls`. It returns public projections only: `{bodies,groups,souls,nextBody}`. Profile deep links use `/?view=community&handle=...`; URLs do not bypass authorization. The root's `x2-community-search` event and `q` URL parameter open scoped directory search.

- **Body discovery** is explicit opt-in, off by default, normalized and parameterized. Search excludes both directions of a block. Nonexistent and unauthorized private profiles return the same 404. Public projections contain no email, internal subject or credentials. A person already in a shared group can see that group's member identity; opting out of general discovery does not erase existing attributed group research.
- **Group discovery** requires an administrator to choose a unique handle and opt in. Directory metadata may be visible within the existing Site audience; group content still requires current membership. Join requests are persistent, administrator-reviewed and initially grant Viewer access. Owners can pin a Soul from their own group. Existing invitations remain handle-bound, expiring and current-inviter-role checked. An invitation inbox lets the exact authenticated named recipient accept without copying a bearer code. Removal revokes future group reads; replaying an earlier accepted invitation or join decision does not restore access.
- **Messaging** uses one unique sorted participant pair, not a separate identity system. Unknown researchers receive a request with at most one introductory message until acceptance. Shared-group conversations may start active according to configured policy. Preferences allow requests, shared groups only, or no incoming messages. A block prevents discovery, inbox access and new sends in both directions. Conversation lists are bounded to 50 per request; message pages contain 40 with a stable timestamp/id cursor. The pair cap is 100 per Body. Messages are plain text, maximum 4,000 characters, with React escaping.
- **Durable state** is `SENT_TO_SERVER`, `RECEIVED`, optionally explicit `READ`, or `RETRACTED`; no simulated delivered channel, online indicator, typing status or end-to-end-encryption claim exists. Read receipts are off by default and appear only when the recipient opts in and explicitly acknowledges a real message in that conversation. Sending does not imply that the recipient has opened it.
- **Editing and retraction** require the sender, current version and author-scoped SQL. Editing is allowed for 15 minutes. Retraction clears text and the Soul reference for both participants, leaving timestamps/version attribution. Hiding affects only the participant's inbox; muting suppresses future message notifications. Draft text remains in component memory on a failed send; leaving/unmounting the component is not represented as durable draft storage.
- **Research references** store a Soul ID and exact revision, never copied restricted source datasets. Both participants must be current members before sending. Every opening rechecks the viewer's membership; a revoked reference projects an unavailable state. The group Soul card's Share in message action sets an explicit pending reference; sending remains a separate deliberate action. Recipients do not acquire a new grant by receiving the ID.
- **Group discussion** supports persistent text, replies, optional HTTPS source link and real observation date. Raw restricted datasets should not be pasted. Retry keys are author/group scoped; changing a payload under the same key conflicts. Mention notifications are generated only for actual existing group members. Group administrators can remove a discussion; authors can remove their own. Removal clears content/source fields and retains a tombstone.
- **Bookmarks** are private and store permitted Bodies or Souls. Current access is rechecked on projection, so private/revoked content cannot leak through a stale saved item. Removal is allowed even after access has been revoked. The cap is 100, and a cap failure does not claim that a new item was saved.
- **Notifications** are persistent records generated from actual messages, mentions and join decisions. Current handle-bound invitations are read from the existing invitation table. Preferences control future persisted notifications; historical notifications and actionable invitations are not silently erased. Visible polling is bounded to 15 seconds, pauses in hidden documents, and creates no simulated presence.

## Data, auth and mutation boundaries

Eleven additive tables are defined in `db/x2-social.ts`: preferences, blocks, conversations, participant views, messages, notifications, bookmarks, reports, group directory, join requests and discussions. The integrator generates one combined production migration. `tests/x2-social-schema.sql` is a drizzle-kit-generated fixture of this same schema, used only when the integrated migration has not yet created the X2 tables. It is not a second production migration.

Every request uses native Sites identity. Every mutation additionally requires the existing current adult/privacy/terms consent and a Body. Same-origin JSON, a 16 KiB streamed body ceiling, input bounds and per-subject rate limits are enforced. Reads are private/no-store. Database values are parameterized. There is no user SQL, remote-source fetching, file upload or secret storage in this subsystem. Error responses expose a classified safe message rather than a raw DB error.

Unique constraints enforce canonical conversation pairs, author/thread/request message keys, author/group/request discussion keys and participant-scoped bookmarks. Ten rapid same-key sends store exactly one message; changed retry payloads return 409. Conditional SQL rechecks current group role at directory/discussion writes. An attempt-specific join-review claim prevents an old accepted request from silently restoring removed membership. These paths are exercised by actual race-injection tests. Existing X1 invitation creation uses its existing code/expiry semantics; the new UI guards the first tap, but duplicate legacy invitations after a lost response are not claimed impossible under all network races.

Messages do not accept attachments, arbitrary inline HTML or remote media. Optional source links require HTTPS without embedded credentials; no server fetch is made. Source dates must be real non-future calendar dates. DMs and reports are never included in public search. There is no public research publishing activation in this release.

## Reports and moderation

Message reports require participation in the reported conversation. Body reports require a permitted profile. Reports persist privately with a reason and timestamp, with a daily cap. Ordinary API responses do not expose another user's report. Existing X1 group-post moderation remains available. Owner-wide DM-report adjudication/retention operations are not exposed to ordinary users; the authorized owner can inspect the stored report table through Site database administration. An automated abuse classifier or an audited dedicated moderation console is not claimed.

## Portability, erasure and retention

`exportSocial(subject)` is integrated by the release owner into the existing authenticated account export. It includes that user's preferences, blocks, bookmarks, notices, reported cases, authored discussions and conversations/messages in which the person participates. It never includes a stranger's DM thread or report. Bounded exports fail with 413 rather than silently dropping records. Exact limits are 100 conversations, 5,000 messages, 5,000 authored discussion items and 1,000 small records per category; larger exports require a complete owner database export.

`socialEraseStatements(subject)` is intended only for the existing explicitly confirmed account-erasure transaction. **Paired conversation deletion removes the recipient's copy of that entire conversation as well.** Foreign-key deletion of a Body has the same conversation cascade. The integrator must require a separate `confirmSharedConversationDeletion` acknowledgement whenever paired conversations exist, in addition to its existing owned-group acknowledgement. No hosted account erasure was run. Other unrelated accounts, conversations and group content remain scoped. Shared X1 group ownership continues to use the original transfer/deletion policy.

There is no unannounced timer deleting active research or messages. Retraction and explicit account erasure are the implemented deletion mechanisms; deployment storage encryption/retention guarantees are not independently audited here. No end-to-end encryption, forensic erasure or automatic GDPR/SEBI certification is claimed.

## Executed verification

`node --experimental-strip-types --experimental-vm-modules --test tests/x2-social.test.mjs`: **14 tests passed, 0 failed** on the isolated SQLite/D1 adapter. Tests exercise native auth/origin/size boundaries; opt-in discovery and escaping; canonical pairs under ten concurrent starts; first-message request gating; ten same-key message retries; cross-user ID denial; read-receipt opt-in; mute/hide; author/version edits and retraction; directory/join privileges; dual-member references and revoked access; scoped threaded discussion and malformed dates/URLs; handle-bound invitations; mid-operation role revocation; member removal/old-approval replay; block/optout privacy; policy/report/export/erasure scoping and SQLite integrity.

Typecheck and scoped lint passed at the first integration checkpoint. The release owner runs final integrated typecheck/lint/build and real browser QA after the follow-up. These fixture tests are not production two-person sessions, a full browser/accessibility audit or physical Android proof. No fixture Body, message, engagement or research result is seeded into production.
