# Community security and browser evidence

See [X2_COMMUNITY_SECURITY.md](X2_COMMUNITY_SECURITY.md) for schema and permission design. Fourteen focused actual API/SQLite social tests cover discovery opt-in, request/send/accept rules, conversation participant isolation, blocks, mute/hide, versioned references, invitation membership/expiry, SQL-time role checks, concurrent pair uniqueness, removed members and retry races. Existing group/publication/comment tests also remain in the full 244-test pass.

An isolated built-Worker browser test used two separate loopback origins with fixed local test identities. Recipient created an explicitly TEST ONLY Body; discovery was initially unchecked and was explicitly opted in. Sender discovered/saved that Body, opened a request and sent one introduction. Recipient observed one unread request, accepted and replied. Sender then observed the real reply and unread count. Both marked read; receipts stayed disabled by default. Screenshots `x2-discovery-390.jpg`, `x2-dm-390.jpg`, `x2-dm-peer-desktop.jpg` are local QA, not live social engagement. The test identities/rows are never imported into production.

No production audience expansion was authorized. Site-level restricted access remains unchanged; app-layer discovery cannot bypass the Site gate. DMs are participant-only server records, not end-to-end encrypted. Separate acknowledgment is required for account erasure affecting shared conversations, and export is participant-scoped; an actual API regression verifies no-ack refusal and peer-account preservation. No production deletion was performed.

No fake researcher activity, online dots or typing indicators is supplied. Removed participants lose group references even when an earlier invitation approval is replayed. A group Soul reference always identifies its exact revision. Current production only has the existing owner; a true multi-person hosted sign-in journey is unverified until the owner separately authorizes the desired audience/onboarding.
